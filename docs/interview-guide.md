# 把项目讲清楚

## 先用一分钟说明

SupportDesk AI 是一个售后协作练习：客户在自己的订单上提出问题，客服在一个页面里查看订单、沟通记录和处理进度，再查询内部资料。可选的本地 AI 可以帮助查规则、核对订单和起草回复，客服看过并确认后，回复才会进入工单。

这是使用虚拟数据、借助 AI 辅助完成的学习项目。介绍时应说明自己实际运行、修改和验证过哪些部分；不要把仓库里的全部代码直接说成已经独立熟练掌握，也不要说成企业实习或生产系统。

## 五分钟演示顺序

1. 登录客户账号，在订单上创建售后工单，补充一条说明。
2. 退出并登录客服，搜索该工单，回复客户，改为处理中。
3. 打开两次同一工单，在一个页面先修改；另一个页面提交旧版本时得到 409，刷新后才能继续。
4. 使用资料检索演示，展示文件名、行号和原文，说明此时没有调用模型。
5. 若已配置且实际运行通过，再演示模型调用工具及草稿。发布前检查内容，确认后查看工单消息和事件；重复发布会被拒绝。
6. 切到另一家虚拟企业的账号，说明服务端如何限制数据范围。页面不显示别人的数据还不够，接口查询也必须检查身份。

## 常见追问的答题要点

**工单和普通留言有什么区别？** 这里的工单绑定订单，包含处理状态、版本和事件记录。留言只是工单中的沟通内容；状态和版本帮助多名客服协作。

**怎么防止客户改个编号就看到别人的订单？** 服务端从登录会话取得账号身份，查询限定企业；客户查询还限定客户编号。客户端不能自己提交身份。越界编号与不存在编号都返回 404。对应 `SupportService` 和 HTTP 权限测试。

**为什么既有行锁又有版本？** 行锁把同一工单的数据库修改排队，版本号用来判断页面里的内容是否已经过时。后来的请求即使等到锁，也不能拿旧页面覆盖新结果。

**为什么要事务？** 一次回复会影响消息、工单版本与事件。它们应该一起成功或一起失败，避免出现“有消息却没有事件”或“版本变了但回复没保存”。可以查看回滚和并发测试。

**AI Agent 与普通聊天接口的区别是什么？** 本项目把工具说明交给模型，模型先选择受限工具，Java 执行后把结果返回给模型，再生成答案。没有给模型任意 SQL、终端或网络访问能力。

**RAG 在这里做了什么？** 先从本企业资料中检索相关片段，再把片段交给模型作为依据。当前使用 BM25 词法检索、中文字符与相邻双字，不是向量数据库；保留文件名和行号便于核对。

**为什么不让 AI 自动发回复？** 查到的资料或模型结论仍可能不适合当前情况。工具只生成草稿，客服显式确认才能发布。发布时再次检查原客服、企业、工单、原版本、草稿状态和到期时间；草稿有效期十分钟。

**如何防止模型编造引用？** 服务端只接受本次实际工具检索得到的来源编号，并校验引用结构。这个检查不能证明自然语言结论一定正确，所以仍显示原文并保留人工审核。

**如果客户在草稿生成后又补充了消息？** 工单版本已经增加，原草稿发布会收到冲突。即使客户端把新版本填上，也不能绕过草稿绑定的原始版本，需要重新核对和生成。

**没有 Ollama 可以运行吗？** 可以。订单、工单、客服回复、资料管理和检索演示都不依赖模型。检索演示不生成草稿，不能把它描述成真实模型调用。

**测试能证明什么？** 真实 HTTP 测试检查登录、权限、事务、并发与工具协议；脚本化模型便于稳定制造错误场景。它们不能证明某个真实模型在所有问题上都答得好。真实模型要另行记录版本、机器环境、问题与成功或失败结果。

**目前有什么可继续改进？** 可增加真实账号管理、完整审计管理页、部署配置和更系统的检索评测。先给出当前代码与实际验证，再说后续计划，不能把计划写成已经完成。

## 放进简历时的边界

可围绕“客户与客服完整流程”“数据隔离与并发冲突”“带来源的检索与人工确认草稿”描述实际项目功能。不要虚构实习公司、上线用户数、吞吐量、准确率或节省成本。刚完成的学习项目应使用真实时间，并在面试前亲自运行流程、定位代码和修改一个小功能。
